## Architecture

`aff audit` keeps printing advisory JSON. When a usable store is present, it also records `project:evidence-observation` rows through the shared recorder used by verdict (CLI subprocess, no runtime import). Technique ids distinguish audit vs probe runs. `replay` carries enough argv/rev metadata to re-run. No bindings are created here.

```
aff audit --> stdout JSON (unchanged meaning)
          \-> evidence-observation(s) unbound + replay
aff trail --technique <audit|probes> --> those rows
```

## Interfaces

- Recorder: shared helper in `affidavit/` (extend observation module) accepting technique, revs, result, optional replay.
- Technique ids: stable strings for audit and probes (exact spelling fixed at implement).
- Trail filter: existing `aff trail --technique` against those ids.

## Decisions

- `technique-record-default`

## Invariants

- Unbound by default; earn only via `evidence-bind` verbs.
- Optional store: no store ⇒ no record, JSON/exit preserved.
- Mutants/blocks remain advisory; recording does not change verdict.

## Assumptions

- Bind phase’s “record ≠ earn” rule is in force.
- Probe outcomes already appear in audit JSON and can be mirrored into observations.

## Tradeoffs

- Default record vs `--record` flag: chose default when store usable for trail completeness.
- Shared helper vs audit-local create: chose shared helper so envelope stays one shape.

## Risks

- Large audit runs create many observations — mitigate with one observation per logical technique unit agreed in tasks, not one row per hunk unless needed.
- Replay metadata drift if argv templates change — pin technique id + rev pair in the observation.
